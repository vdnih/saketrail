# 開発プロセスガイドライン

## 基本方針

SakeTrailプロジェクトでは、以下の開発方針に従って開発を進めます：

1. **ドキュメント駆動開発（Documentation Driven Development）**
   - 新機能の実装前に必ずドキュメントを作成
   - 設計変更時はドキュメントを先に更新
   - 実装完了後、実装内容とドキュメントの整合性を確認

2. **MVPアプローチ（Minimum Viable Product）**
   - 小さな機能単位での開発
   - 段階的な機能追加
   - 各段階でのユーザー価値の確保

3. **品質管理**
   - コードレビューの徹底
   - テストカバレッジの維持
   - 継続的なリファクタリング

## 開発フロー

### 1. 機能追加/変更の流れ

1. **計画フェーズ**
   - 機能要件の定義
   - MVPスコープの決定
   - タスクの分割と優先順位付け

2. **ドキュメント作成フェーズ**
   - 機能仕様書の作成/更新
   - API仕様書の作成/更新（必要な場合）
   - アーキテクチャドキュメントの更新（必要な場合）

3. **実装フェーズ**
   - ブランチの作成（`feature/[機能名]`）
   - テストの作成
   - 機能の実装
   - コードレビュー

4. **検証フェーズ**
   - 単体テストの実行
   - 結合テストの実行
   - ドキュメントとの整合性確認

5. **リリースフェーズ**
   - mainブランチへのマージ
   - デプロイ
   - リリースノートの作成

### 2. ドキュメント管理

#### 2.1 ドキュメントの種類と配置

- `/docs/architecture/` - アーキテクチャ設計書
  - `overview.md` - システム概要
  - `infrastructure.md` - インフラ構成
  - `data-model.md` - データモデル
  
- `/docs/api/` - API仕様書
  - `endpoints/` - エンドポイント定義
  - `models/` - データモデル定義
  
- `/docs/guides/` - 各種ガイドライン
  - `development-process.md` - 本ドキュメント
  - `coding-standards.md` - コーディング規約
  - `testing.md` - テストガイドライン

#### 2.2 ドキュメント更新ルール

- 実装変更を行う場合は、必ず関連するドキュメントも更新
- ドキュメントの更新は同じPRに含める
- レビュー時にドキュメントの整合性も確認

### 3. MVPの進め方

#### 3.1 基本原則

- 1つの機能を小さく分割して実装
- 各機能は独立してリリース可能な単位とする
- ユーザーにとって価値のある最小単位で実装

#### 3.2 機能分割の例

悪い例：
```
- 日本酒登録機能（画像認識、情報入力、レビュー、共有機能を一度に実装）
```

良い例：
```
1. 基本的な日本酒情報の手動登録
2. 画像からのラベル情報読み取り
3. 詳細情報の入力機能
4. レビュー機能
5. SNS共有機能
```

#### 3.3 優先順位付け

- ユーザー価値の高さ
- 技術的な依存関係
- 実装の複雑さ

を考慮して優先順位を決定

### 4. 品質管理

#### 4.1 コードレビュー基準

- 機能要件との整合性
- コーディング規約との整合性
- テストの網羅性
- ドキュメントの更新確認

#### 4.2 テスト要件

- ユニットテストカバレッジ 80%以上
- 重要な機能の結合テスト
- UIコンポーネントのウィジェットテスト
