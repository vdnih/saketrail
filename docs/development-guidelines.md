# 開発ガイドライン

## コーディング規約

### 1. 全般的なルール
- インデントは2スペースを使用
- 文字コードはUTF-8
- 改行コードはLF
- ファイル末尾は空行で終わる

### 2. 命名規則

#### フロントエンド（TypeScript/Next.js）
- **コンポーネント**: PascalCase（例: `UserProfile.tsx`）
- **関数**: camelCase（例: `getUserData`）
- **変数**: camelCase（例: `userData`）
- **定数**: SNAKE_CASE（例: `MAX_RETRY_COUNT`）
- **型定義**: PascalCase（例: `interface UserData`）

#### バックエンド（Python/FastAPI）
- **クラス**: PascalCase（例: `UserService`）
- **関数/メソッド**: snake_case（例: `get_user_data`）
- **変数**: snake_case（例: `user_data`）
- **定数**: SNAKE_CASE（例: `MAX_RETRY_COUNT`）

### 3. コメント規約

- コードの「なぜ」を説明する
- 自明なコードにはコメントを書かない
- 複雑なロジックには必ずコメントを付ける
- 日本語でのコメントを推奨

```typescript
// 良い例
// ユーザーの年齢が20歳以上かつ、メール認証が完了している場合のみ
// 投稿を許可する
if (user.age >= 20 && user.isEmailVerified) {
  allowPost();
}

// 悪い例
// ユーザーの年齢をチェック
if (user.age >= 20) {
}
```

### 4. コンポーネント設計

#### フロントエンド
- アトミックデザインの採用
  - atoms: 最小単位のUI要素
  - molecules: atomsの組み合わせ
  - organisms: 複数のmoleculesの組み合わせ
  - templates: ページのレイアウト
  - pages: 実際のページコンポーネント

#### バックエンド
- レイヤードアーキテクチャの採用
  - Controller: リクエストの受付
  - Service: ビジネスロジック
  - Repository: データアクセス

### 5. テスト規約

#### テストの種類
1. **ユニットテスト**
   - 関数/メソッドの単体テスト
   - モックを活用

2. **統合テスト**
   - APIエンドポイントのテスト
   - DBアクセスを含むテスト

3. **E2Eテスト**
   - ユーザーシナリオベースのテスト
   - 重要な機能フローのテスト

#### テストの命名規則
```typescript
describe('UserService', () => {
  describe('createUser', () => {
    it('正常なデータで新規ユーザーを作成できる', () => {
      // テストコード
    });

    it('無効なメールアドレスでエラーを返す', () => {
      // テストコード
    });
  });
});
```

### 6. Git運用ルール

#### ブランチ戦略
- main: プロダクション環境
- develop: 開発環境
- feature/*: 機能開発
- fix/*: バグ修正
- release/*: リリース準備

#### コミットメッセージ
```
feat: ユーザー登録機能の追加
^--^  ^----------------------^
|     |
|     +-> 変更内容の要約
|
+-------> コミットタイプ
```

コミットタイプ:
- feat: 新機能
- fix: バグ修正
- docs: ドキュメントのみの変更
- style: コードの意味に影響しない変更（空白、フォーマット等）
- refactor: リファクタリング
- test: テストコードの追加・修正
- chore: ビルドプロセスやツールの変更

### 7. コードレビュー基準

#### レビュー項目
1. **機能要件**
   - 仕様通りに動作するか
   - エッジケースの考慮

2. **非機能要件**
   - パフォーマンス
   - セキュリティ
   - 保守性

3. **コード品質**
   - 命名の適切さ
   - コードの重複
   - テストの充実度

#### レビューコメントの書き方
```
[必須] セキュリティ: ユーザー入力のサニタイズが必要です
[提案] 可読性: この関数は小さな関数に分割できそうです
[質問] なぜこの実装方法を選択したのでしょうか？
```
